## 2. Cryptographic & Hash Format Analysis

### 2.1 Password Hashing Specification
- **Storage Location:** `auth.users.encrypted_password`
- **Algorithm:** Modular Crypt Format standard **bcrypt** (`$2a$` or `$2b$`)
- **Cost Factor / Rounds:** `10` (default in Supabase GoTrue)
- **Hash Structure:**
  ```text
  $2a$10$N9qo8uLOickgx2ZMRZoMye.I...53-character-salt-and-ciphertext...
   ^   ^  ^
   |   |  +-- 22-character Base64 Salt
   |   +----- Cost Factor (10 = 2^10 = 1,024 iterations)
   +--------- Bcrypt Variant Identifier
  ```
- **Verification Guarantee:** Bcrypt hashes are self-contained. The salt and cost parameters are encoded directly in the hash string. When target GoTrue (or any standard bcrypt library) receives a password at login, it reads the embedded salt and cost, hashes the incoming candidate plaintext, and executes a constant-time comparison against the ciphertext.
- **Result:** Existing passwords function seamlessly in the target environment. No user accounts are invalidated; no password reset emails are triggered.

### 2.2 JWT Signing Keys & PostgREST Synchronization
- In Supabase architecture, GoTrue acts as the token issuer, while PostgREST acts as the token verifier.
- Both services share a single secret: `JWT_SECRET`.
- **Token Claims Generated by GoTrue:**
  ```json
  {
    "sub": "3d9c8e21-5a41-4c7b-b892-0b61e2049d5a",
    "aud": "authenticated",
    "role": "authenticated",
    "email": "minister@example.com",
    "app_metadata": {
      "provider": "email",
      "providers": ["email"]
    },
    "user_metadata": {
      "full_name": "Pastor David",
      "country": "Nigeria"
    },
    "exp": 1729810000,
    "iat": 1729806400
  }
  ```
- **Target Configuration Requirement:** In `docker-compose.yml`, both `GOTRUE_JWT_SECRET` and `PGRST_JWT_SECRET` must be set to the exact same high-entropy string ($\ge 64$ characters). PostgREST uses this shared secret to cryptographically verify incoming bearer tokens and populate `auth.uid()` and `request.jwt.claims` for Row Level Security policies.

## 4. Session Transition & Frontend Client Configuration

### 4.1 Client Storage Configuration
In `src/integrations/supabase/client.ts`, the application currently references `brokeredPreviewStorage()` from `previewAuthStorage.ts`. This was implemented solely for the Lovable web editor preview iframe.

```typescript
// TARGET CONFIGURATION (Independent Deployment)
import { createClient } from '@supabase/supabase-js';
import type { Database } from './types';

const SUPABASE_URL = import.meta.env.VITE_SUPABASE_URL; // Points to https://api.ismprayernetwork.org
const SUPABASE_PUBLISHABLE_KEY = import.meta.env.VITE_SUPABASE_PUBLISHABLE_KEY; // Target Anon Key

export const supabase = createClient<Database>(SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, {
  auth: {
    storage: localStorage, // Native standard browser storage
    persistSession: true,
    autoRefreshToken: true,
    detectSessionInUrl: true,
  }
});
```

### 4.2 Handling Active User Sessions on Cutover Day
1. **Access Token Lifespan:** Active JWT access tokens expire naturally after 60 minutes (`GOTRUE_JWT_EXP = 3600`).
2. **Refresh Token Exchange:** If the target GoTrue instance is provisioned with the existing `JWT_SECRET`, valid refresh tokens in users' `localStorage` will exchange silently on background refresh requests without interrupting active sessions.
3. **Graceful Fallback:** If a client session fails refresh (e.g. if the refresh token expired during the maintenance window), `AuthContext.tsx` handles the transition gracefully, presenting the clean sign-in modal. Entering existing credentials logs the user in immediately.

## 5. User Migration Pre-Flight Verification Script

Run this SQL verification against the restored target database prior to DNS cutover to ensure authentication data readiness:

```sql
DO $$
DECLARE
  v_user_count bigint;
  v_confirmed_count bigint;
  v_unhashed_count bigint;
  v_orphan_profiles bigint;
BEGIN
  -- 1. Check total users
  SELECT count(*) INTO v_user_count FROM auth.users;
  RAISE NOTICE 'Total users in auth.users: %', v_user_count;

  -- 2. Verify all passwords are encrypted with bcrypt
  SELECT count(*) INTO v_unhashed_count FROM auth.users 
  WHERE encrypted_password IS NULL OR encrypted_password NOT LIKE '$2%';
  
  IF v_unhashed_count > 0 THEN
    RAISE EXCEPTION 'CRITICAL: % user accounts have invalid or missing bcrypt hashes!', v_unhashed_count;
  ELSE
    RAISE NOTICE 'SUCCESS: 100% of user password hashes use valid bcrypt formatting.';
  END IF;

  -- 3. Verify confirmed emails
  SELECT count(*) INTO v_confirmed_count FROM auth.users WHERE email_confirmed_at IS NOT NULL;
  RAISE NOTICE 'Verified email accounts: % of %', v_confirmed_count, v_user_count;

  -- 4. Check for orphan profiles
  SELECT count(*) INTO v_orphan_profiles FROM public.profiles p
  WHERE NOT EXISTS (SELECT 1 FROM auth.users u WHERE u.id = p.user_id);

  IF v_orphan_profiles > 0 THEN
    RAISE WARNING 'WARNING: % profile records have no corresponding auth.users entry!', v_orphan_profiles;
  ELSE
    RAISE NOTICE 'SUCCESS: Zero orphan profiles detected. 100% relational integrity.';
  END IF;
END $$;
```
